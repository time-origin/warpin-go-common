# 银盛小 Y 聚合收银台 APP 支付公共模块封装计划

日期：2026-09-03  
状态：已批准并完成协议冻结，公共模块开发中  
目标仓库：`github.com/time-origin/warpin-go-common`  
目标目录：`payment/ysepay`

## 1. 选型结论

本项目选择“小 Y 聚合收银台”的 APP 场景，不继续使用 A00171 支付宝 APP 支付作为主接入方案。

选型原因：

1. 业务目标是同一个 iOS/Android App 支持微信和支付宝。
2. 小 Y 聚合收银台明确支持 APP 端的微信小程序支付和支付宝支付。
3. 两个渠道共用一套服务端预下单、查询、退款、通知和安全协议，由 `payMode` 区分支付方式。
4. A00171 是支付宝单渠道产品，无法单独完成微信+支付宝的产品目标。

这里的“聚合收银台”是支付产品，“APP”是客户端承载形态，两者不冲突。

## 2. 目标与范围

本期在 `payment/ysepay` 实现银盛聚合收银台的 Go 协议客户端，包括：

1. 聚合收银台预下单。
2. 支付宝 APP 场景的拉起数据解析。
3. 微信 APP 拉起小 Y 收银台小程序所需数据的解析。
4. 聚合支付结果异步通知的验签和解析。
5. 交易结果明细查询。
6. 交易退款。
7. 退款交易查询。
8. 公共请求加密、加签、响应验签与解密。

本期不实现：

- 支付宝 A00171 旧表单网关客户端。
- 业务订单、支付或退款状态机。
- 数据库模型、Repository 和事务落库。
- HTTP 业务路由、用户权限和客户端 API 响应包装。
- Flutter 端的 WebView、微信 SDK 和应用回跳实现。
- 官方聚合收银台接口列表未包含的关单和对账能力。如后续需要，必须先取得对应官方契约。

### 3.1 双渠道 APP 契约

| 支付方式 | `payMode` | APP 拉起方式 | 公共模块返回 |
| --- | --- | --- | --- |
| 支付宝 | `26` | 优先使用预下单 `payUrl` 通过 WebView 打开；正式环境也可能只返回 `encryData` | 经验签、解密和校验的 `payUrl/encryData` |

### 3.3 商户身份模型

本项目在银盛体系中同时存在两个逻辑身份，不能用一个笼统的“商户号”字段代替：

```text
银盛/上级服务商
       │
       ▼
二级代理商（接口发起方）
持有接口签名凭据并发起银盛请求
       │
       ▼
本公司已签约的银盛二级商户（`mercId`）
作为银盛接口中的收款方
       │
       ▼
微信/支付宝渠道商户（银盛所有并维护）
```

业务仓使用本公司已经完成签约的银盛二级商户身份收款。它不配置微信或支付宝渠道商户号；底层渠道交易由银盛自己的渠道商户承接。

| 银盛概念 | 接口位置 | 本项目含义 | 生命周期 |
| --- | --- | --- | --- |
| 服务商商户号/发起方商户号 | 公共字段 `certId` | 二级代理商或供应商确认的接口发起方身份 | 跟随接入凭据配置 |
| 银盛二级商户号 | `bizContent.mercId` | 本公司已签约的银盛侧收款身份 | 跟随银盛商户签约配置 |
| 业务代码 | `bizContent.busiCode` | 银盛二级商户已开通的结算产品 | 跟随商户签约权限 |
| 商户订单号 | `bizContent.orderId` | 业务仓生成的支付订单号 | 每笔订单唯一 |

官方通知文档列出的业务代码中，`00510102` 表示“聚合收银台 D0”，`00510103` 表示“聚合收银台”。业务仓不得自行选择或切换，必须使用该银盛二级商户实际获批的代码。

费率和签约产品属于银盛商户配置，不是每笔支付请求参数，也不属于 `payment/ysepay` 公共模块职责。若后续接入银盛商户管理能力，应作为独立模块设计，不与支付下单客户端混合。

本公司已作为银盛二级商户完成签约。实际微信、支付宝交易使用银盛体系的渠道商户号，由银盛负责配置和维护，不要求本公司另行申请或报备自有渠道商户号。当前预下单只传 `mercId/busiCode/payMode`，公共模块不新增微信商户号、支付宝商户号或自有微信 `AppID` 字段。

## 4. 新网关安全协议

请求为 `application/json`，公共字段包括：

- `timeStamp`
- `method`
- `charset=utf-8`
- `sign`
- `check`
- `bizContent`
- `reqId`
- `certId`
- `version`

官方协议流程：

1. 生成随机 AES 密钥。
2. 使用 AES 加密业务 JSON，得到 `bizContent`。
3. 使用银盛公钥加密 AES 密钥，得到 `check`。
4. 使用接口发起方的 `.pfx` 所含私钥对请求签名，得到 `sign`。
5. 收到同步响应后，先使用银盛公钥验签，再解密 `businessData`。
6. 验签、解密或必要字段校验任一失败，都不向业务层返回可使用的成功数据。

官方 Java Demo 已确认 `.pfx/.cer` 组合使用 RSA：请求签名为 SHA256withRSA，`check` 为 RSA/ECB/PKCS1Padding，业务报文为 AES/ECB/PKCS5Padding（Go 中等价实现为 PKCS7），编码使用标准 Base64。顶层字段按名称升序、排除 `sign` 和 Demo 注入字段 `$jacocoData` 后以 `key=value&...` 拼接，不做 URL 编码。供应商交付的不是 `.sm2` 材料，因此本期不实现国密分支。

### 4.1 证书和密码的作用

| 材料 | 作用 | 敏感级别 | 存放位置 |
| --- | --- | --- | --- |
| 发起方 `.pfx` | PKCS#12 签名证书，通常包含请求签名私钥和证书链 | 最高敏感 | 仅业务侧服务器的 Secret/密钥存储 |
| PFX 密码 | 解锁 `.pfx` 私钥 | 最高敏感 | 仅 Secret/密钥管理系统，不写配置文件 |
| 银盛 `.cer` | 银盛公钥证书，用于响应/通知验签，并按官方协议加密随机 AES 密钥 | 公钥但需保证来源完整性 | 业务侧服务器运行时提供 |
| 服务商商户号 | 标识请求发起方，通常填写 `certId` | 内部配置 | 业务侧服务器运行时提供 |

`.pfx` 的实际归属必须由供应商书面确认：它应当与 `certId` 所代表的发起方身份匹配。如果证书属于上级服务商且在多个二级代理商之间共享，应重新评估密钥隔离和部署方式，不允许无边界复制到多个业务系统。

## 5. 责任边界

| 能力 | `warpin-go-common/payment/ysepay` | 业务仓 | Flutter App |
| --- | --- | --- | --- |
| 发起方凭据 | 接收证书内容/签名器并校验必要配置 | 从 Secret/密钥管理服务加载 `.pfx`、密码、`.cer` 和 `certId` | 不接触任何服务端凭据 |
| 收款商户 | 接收每次请求的 `mercId/busiCode` | 使用本公司已签约的银盛二级商户配置 | 不提交微信或支付宝渠道商户号 |
| 安全报文 | AES 加解密、密钥加密、加签、验签 | 不复制协议实现 | 不复制协议实现 |
| 支付下单 | 组装银盛报文并解析拉起数据 | 创建本地订单、校验金额与权限 | 选择支付方式并请求业务后端 |
| 支付宝拉起 | 返回已校验 `payUrl` | 只返回必要客户端字段 | 通过 WebView 打开 |
| 微信拉起 | 返回已校验 `appId/businessData` | 组装最小拉起响应 | 通过微信 SDK 打开收银台小程序 |
| 支付通知 | 先验签，再返回类型化结果 | HTTP 路由、限流、幂等和事务落库 | 客户端回跳不作为支付成功依据 |
| 查询/退款 | 调用银盛并返回类型化结果 | 拥有业务状态机和退款幂等 | 只展示业务后端状态 |

服务商商户号、银盛二级商户号、业务代码、`.pfx`、证书密码和银盛 `.cer` 由业务仓在运行时注入。微信/支付宝渠道商户号属于银盛，不作为公共模块或业务仓配置；客户端确需的银盛收银台公开 AppID 仅按银盛响应或客户端接入规范使用。公共仓源码、测试、文档和日志不得包含真实值。

推荐部署关系：

```text
业务侧服务器的 Secret/密钥管理系统
  ├── 发起方签名证书.pfx
  ├── PFX 密码
  ├── 银盛公钥证书.cer
  └── 发起方商户号 certId
                 │ 运行时读取
                 ▼
业务仓支付服务
  ├── 选择已签约银盛二级商户 mercId
  ├── 选择已获批业务代码 busiCode
  └── 创建本地业务订单
                 │ 通过类型化参数调用
                 ▼
warpin-go-common/payment/ysepay
  └── 签名、验签、加解密、请求和响应解析
```

## 6. 公共模块设计

### 6.1 目录

```text
payment/
└── ysepay/
    ├── client.go
    ├── config.go
    ├── crypto.go
    ├── errors.go
    ├── notification.go
    ├── types.go
    └── *_test.go
```

当前只实现银盛聚合收银台，不创建只有一个实现的泛化 Payment Provider Registry。未来真正引入第二个支付供应商后，再根据已经出现的共性提取最小接口。

### 6.2 配置

业务仓显式构造 `ysepay.Config`。公共模块不自动读取固定环境变量或仓库内配置文件。

| 配置 | 说明 |
| --- | --- |
| `Environment` | 只允许官方 `Test` 和 `Production` |
| `InitiatorMerchantID` | 银盛下发并由供应商确认的发起方商户号，对应 `certId` |
| `SigningPKCS12`/签名器 | 业务仓读取 `.pfx` 后传入的字节或受控签名器，用于请求签名 |
| `SigningCertificatePassword` | 业务仓从 Secret 读取的 PFX 解锁密码；使用外部签名器时不需要 |
| `YsePublicCertificate` | 业务仓读取 `.cer` 后传入的银盛公钥，用于密钥加密、响应和通知验签 |
| `HTTPClient` | 可选；未传时使用带明确超时的安全默认值 |

公共模块配置不接受证书文件路径，也不读取业务服务器固定目录、环境变量或配置中心；文件读取和 Secret 获取由业务仓完成，公共模块只接收内存中的证书材料或签名器。

`MercID`、`BusiCode`、`BackURL` 属于银盛二级商户或订单边界，作为预下单请求的显式字段，不由公共模块猜测默认值。字段命名应区分 `InitiatorMerchantID` 和 `PayeeMerchantID`，避免把 `certId` 与 `mercId` 传反。

官方契约未展示 `apiKey` 字段。如实际开户资料另行下发 API Key，必须根据供应商说明确认其用途后再增加类型化配置，不预留无用密钥字段。

### 6.3 对外方法

```go
client, err := ysepay.NewClient(config)

order, err := client.CreateCashierOrder(ctx, request)
trade, err := client.QueryTrade(ctx, query)
refund, err := client.Refund(ctx, refundRequest)
refundState, err := client.QueryRefund(ctx, refundQuery)

notice, err := client.ParsePaymentNotification(payload)
```

不对外暴露可绕过字段、金额和必填项校验的通用 `map[string]any` 请求入口。

### 6.4 预下单结果

`CreateCashierOrder` 在验签和解密成功后返回：

- `RequestID`
- `OrderID`
- `PayeeMerchantID`
- `AmountFen`
- `CreatedAt`
- `ExpiresAt`
- `PayMode`
- `PayURL`（银盛返回时提供）
- `EncryptedData`（正式环境已验证可能是唯一返回的拉起材料）
- `CashierAppID`（银盛返回时提供，微信场景不强制）
- `BusinessData`（微信小程序拉起必需的完整已验证解密对象）

正式响应的解密对象可能使用 `{rpcError,data,suffixCode}` 包装，公共模块从 `data` 读取订单字段，同时兼容字段位于根对象的历史形式。微信拉起需要把完整解密对象 `BusinessData` 传给收银台小程序。公共模块校验必要字段并保留未知扩展字段，但不在日志或错误中打印完整拉起数据。

## 7. 金额、状态与幂等

### 7.1 金额

1. 预下单、查询和退款协议的主要金额以“分”字符串传输。
2. 公共 Go API 使用 `int64` 分，禁止使用 `float32/float64` 作为交易金额边界类型。
3. 异步通知中的 `amount` 按官方文档以“元”表示，公共模块必须精确转换为分，不经过浮点数。
4. 业务仓在回调事务中将通知金额、订单号、币种和商户号与本地订单逐项比对。

### 7.2 支付状态

交易查询返回的主要状态包括：

- `00`：交易成功。
- `11`：支付中。
- `80/81`：部分/全部退款。
- `50`：业务超时，业务仓应结合查询结果决定是否继续等待或终止订单。
- `93/95/97/99`：撤销或关闭类状态。
- `98`：支付失败。

公共模块保留银盛原始状态，业务仓拥有最终状态机。超时、网络错误、查询空结果和未识别状态保持“不确定”语义，不能直接当作支付失败。

### 7.3 异步通知

1. 通知使用 JSON POST，且必须使用银盛公钥验签。
2. 通知可能重复。业务仓必须在数据库事务中完成唯一性检查、状态迁移和权益发放。
3. 仅在验签、金额校验和事务提交全部成功后返回纯文本 `success`。
4. 非 `success` 回复会触发银盛额外 5 次通知，间隔为 1、5、10、30、60 分钟。
5. App 回跳、微信小程序 `payResult` 和支付宝页面结果不作为服务端支付成功依据。

### 7.4 退款

1. 业务仓对 `refundOrderId` 建立唯一约束，重试复用原请求号。
2. 退款接口的同步成功只表示已受理，不表示资金已成功退回。
3. 最终状态通过 `QueryRefund` 确认。
4. 官方说明微信一个订单最多退款 50 次，业务仓应根据自身业务规则设定更严格上限。

## 8. 错误边界

公共模块提供可使用 `errors.Is/As` 判定的稳定技术错误：

- 未配置或配置无效。
- 请求字段或金额无效。
- 加密、解密、签名或验签失败。
- 银盛通信超时或非预期 HTTP 响应。
- 响应结构无效或缺失必要字段。
- 银盛明确拒绝请求，保留 `code/subCode` 供业务仓映射。
- 交易结果不确定，要求业务仓查询或人工处理。

公共模块不定义 VoiceCraft 业务错误码和面向用户的中文文案。业务仓负责错误码映射，不直接向 App 透传银盛原始响应。

## 9. 安全约束

1. 公共仓不保存真实或示例化的商户号、AppID、API Key、私钥、证书、密码和回调 URL。
2. 业务仓也不得把真实 `.pfx`、PFX 密码或其他生产凭据提交到 Git；优先使用 Kubernetes Secret、云 Secret Manager 或 Docker Secret 挂载。
3. 不建议用启动命令参数传递证书密码；日志、进程列表、崩溃信息和诊断输出均不得暴露密码或证书原文。
4. `.cer` 虽然是公钥，仍由业务侧部署并校验可信来源/指纹，公共模块不内置银盛证书，便于测试/生产隔离和证书轮换。
5. 公共模块不记录完整请求、完整回调、`sign`、`check`、AES 密钥、`businessData`、`encryData` 或付款人信息。
6. 响应体有严格大小上限，HTTP Client 必须有超时。
7. 密码学随机数使用 `crypto/rand`，不使用可预测随机源。
8. 敏感缓冲区在可行范围内尽快清理，不向错误链附加密钥内容。
9. 测试使用运行时生成的临时密钥，不收录真实商户报文。
10. 测试和生产使用不同证书；证书到期、吊销或轮换时由业务侧部署流程替换，不需要发布公共模块新版本。

## 10. 实施顺序

1. 获取供应商官方 demo、非敏感加密/签名样例向量，确认算法与预下单版本。
2. 实现环境、配置、精确金额、支付方式与稳定错误分类。
3. 按官方样例向量实现 AES、密钥加密、加签和验签。
4. 实现预下单，同时覆盖 `payMode=26` 和 `payMode=29`。
5. 实现支付通知验签解析和交易查询。
6. 实现退款与退款查询。
7. 完成公共模块单元测试、README 入口和业务仓接入示例。示例只使用占位符，不包含可用凭据。
8. 公共模块验收后，再在业务仓实现订单、回调、幂等状态迁移和 Flutter 拉起契约。

## 11. 验证计划

单元测试覆盖：

- 缺失必要配置时明确失败。
- `.pfx` 无法解析、密码错误、证书类型不支持时明确失败且错误不包含凭据。
- `InitiatorMerchantID`、`PayeeMerchantID` 和 `BusiCode` 分别映射到 `certId`、`mercId` 和业务代码，不允许混用。
- 测试/生产环境只能选择官方固定网关。
- `reqId` 长度、字符集、唯一性责任和末 12 位时间格式。
- 订单号、有效期、金额、币种、必填项与 `payMode` 校验。
- 官方 AES、密钥加密、加签和验签样例向量。
- 篡改任一公共或业务字段后验签失败。
- 未知响应字段向前兼容，必要字段缺失时失败。
- 支付宝 `payUrl` 和微信 `appId/businessData` 的分支校验。
- 异步通知验签、元到分精确转换、缺字段和篡改场景。
- HTTP 超时、非 2xx、空响应、超限响应和非法 JSON。
- 不同操作的 `code/subCode` 成功值和不确定结果。
- 错误和可记录元数据中不包含敏感值。

验证命令：

```bash
go test ./...
go test -race ./...
go vet ./...
```

单元测试使用自定义 `http.RoundTripper` 和临时密钥，不调用真实网关。真实联调在业务仓通过本地 Secret 或部署平台 Secret 注入资料。

## 12. 验收条件

1. 公共仓没有任何真实商户号、AppID、API Key、证书、私钥、密码或回调地址，也不包含固定证书路径。
2. 业务仓可从服务器 Secret 读取并通过显式 `Config` 注入 `.pfx`、PFX 密码、`.cer` 和发起方商户号。
3. `certId` 始终表示接口发起方，`mercId` 始终表示本公司已签约的银盛二级商户，代码、测试和文档不使用含糊的单一 `MerchantID` 表达二者。
4. 预下单同时支持支付宝 `26` 和微信小程序 `29`，且共用一套客户端实现。
5. 所有同步响应和异步通知均先验签，再解密和解析。
6. 支付宝场景返回银盛实际提供的 `payUrl/encryData`，微信场景返回完整 `businessData`，`appId` 存在时原样返回。
7. 通知验签失败、金额无法精确转换或必要字段缺失时，不返回可供业务落库的成功事件。
8. 超时和未知状态不被错误地映射为支付失败。
9. 公共模块无业务数据库、无 HTTP 业务路由、无商户进件/费率配置、无业务错误码、无订单状态机。
10. 所有公共模块自动化检查通过，真实联调结果在业务仓另行记录。

## 13. 公共模块已关闭项与业务仓联调资料

1. 当前银盛二级商户签约产品已包含聚合收银台微信和支付宝生产权限。
2. 供应商官方 Go/Java demo 或完整国密+AES 调用规则。
3. 至少一组不含真实商户凭据的加密、签名、验签和解密样例向量。
4. 预下单 `version` 已通过正式环境最小联调确认使用 `1.4`。
5. APP 场景的 `appType` 值及它与 `payMode=26/29` 的组合规则。
6. 客户端接入确有需要时，由银盛提供生产收银台 AppID、小程序原始 ID 和生产小程序类型。
7. 微信开放平台移动应用 AppID 和 iOS/Android SDK 配置要求。
8. 本公司已签约银盛二级商户的正式 `mercId`，以及实际获批的 `busiCode`（确认使用 D0 `00510102` 还是普通聚合收银台 `00510103`）。
9. 服务商商户号是否就是请求 `certId`，以及 `.pfx` 是否为该 `certId` 专属签名证书的书面确认。
10. `.pfx` 的算法、证书链、密码用途、有效期、测试/生产归属和轮换方式；银盛 `.cer` 的可信指纹。
11. 如另行下发 API Key，需提供官方用途说明。

公共模块开发所需的第 1、2、3、4、5、9、10 项已由官方文档、官方 Java Demo、供应商答复及正式环境最小联调关闭，具体决议见 SDD。底层渠道商户号由银盛维护；客户端确需的银盛收银台公开 AppID 与 SDK 配置只部署在业务侧，不进入公共仓。
