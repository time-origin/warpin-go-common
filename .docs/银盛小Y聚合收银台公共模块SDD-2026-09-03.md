- 小 Y 聚合收银台、APP 前端接入、接口说明、预下单、通知、交易查询、退款、退款查询页面为业务字段基线。
- 银盛官方 Java Demo 为 RSA/AES、签名原文、PFX/CER 解析的互操作基线。
- 预下单修订记录称版本改为 `6.3`，参数表仍写 `1.4`。2026-09-03 正式环境最小联调中，`6.3` 返回“目标资源不存在或已下线”，`1.4` 返回签名成功响应 `code=00000/subCode=0`，因此实现以正式环境实测可用的 `1.4` 为准。
- 官方 APP 文档明确支付宝 `payMode=26`、微信小程序收银台 `payMode=29`。`appType` 可选但没有官方枚举，本期不发送。
- 官方 Demo 的旧 HTTP 示例使用表单和 Base64 包裹响应；当前接口文档明确 JSON POST。请求固定使用 JSON，响应兼容直接 JSON 与整包 Base64 JSON。
- 供应商交付 `.pfx/.cer`，官方 Demo 说明该材料类型对应 RSA；`.sm2` 才对应国密。因此本期仅实现 RSA。
- 官方 Demo 的 PFX 使用 BER 不定长编码，银盛公钥 CER 使用历史负序列号；配置入口需兼容这两种官方材料，但报文密码协议不因此降级。

## 2. 身份、配置与秘密边界

| 公共 API | 银盛字段 | 含义 | 约束 |
| --- | --- | --- | --- |
| `Config.InitiatorMerchantID` | `certId` | 二级代理商/服务商接口发起方 | 与 PFX 成组注入 |
| `CreateCashierOrderRequest.PayeeMerchantID` | `bizContent.mercId` | 本公司已签约的银盛二级商户 | 每笔订单显式传入 |
| `BusinessCode` | `bizContent.busiCode` | 银盛二级商户获批产品 | 仅 `00510102/00510103`，无默认值 |
| `SigningPKCS12` | 无直接报文字段 | 发起方 RSA 私钥与证书 | 仅内存字节 |
| `SigningCertificatePassword` | 无 | PFX 解锁密码 | 仅内存字符串，不进入错误 |
| `YsePublicCertificate` | 无 | 银盛 RSA 公钥 | DER 或 PEM X.509 |

公共模块不读取文件、环境变量或配置中心，不内置商户号、AppID、回调地址和证书。业务侧负责从 Secret 读取材料、区分测试/生产、核对指纹和轮换；轮换通过重建不可变 Client 生效。

本公司已作为银盛二级商户完成签约。实际微信、支付宝交易使用银盛体系的渠道商户号，本公司无需另行申请、报备或配置自有渠道商户号。这些字段不进入 `Config` 或预下单请求；公共模块只按 `payMode` 选择渠道，并透传银盛响应中可供客户端使用的公开 `appId/businessData`。

## 3. 密码协议

1. 将业务对象序列化为 UTF-8 JSON。
2. 使用密码学安全随机源生成 16 个大写十六进制 ASCII 字符作为 AES-128 密钥。
3. 使用 AES/ECB/PKCS7 加密业务 JSON，再用标准 Base64 编码为 `bizContent`。PKCS7 与 Java AES 块大小下的 PKCS5Padding 互操作。
4. 使用银盛证书 RSA 公钥以 PKCS#1 v1.5 加密 AES 密钥，标准 Base64 编码为 `check`。
5. 顶层参数按字段名升序排列，排除 `sign` 与官方 Demo 测试注入字段 `$jacocoData`，连接为 `key=value&key=value`；值不做 URL 编码。
6. 对签名原文 SHA-256 摘要后使用 RSA PKCS#1 v1.5 私钥签名，标准 Base64 编码为 `sign`。
7. 同步响应必须先对顶层字段验签，再判断返回码、解密 `businessData`、校验业务字段。任何一步失败均不返回可消费的成功对象。
8. 通知的 `bizContent` 是明文 JSON 字符串；先对顶层通知验签，再解析和校验业务数据。

证书只要求可解析、为 RSA、私钥与 PFX 证书公钥匹配且当前有效。PFX 的 BER 兼容在内存中进行有大小/深度限制的 DER 规范化并重新计算认证安全区 MAC，不调用外部命令。不得以现代密钥长度、负序列号或证书自身签名算法为由拒绝银盛仍在使用的历史证书；报文签名算法始终是 SHA256withRSA。

## 4. 传输与公共参数

- 只允许 `Test`、`Production` 两种环境，端点固定，不开放自定义 URL。
- 使用 `POST application/json; charset=utf-8`，默认客户端超时 20 秒，禁用自动重定向，响应体上限 1 MiB。
- 写操作不自动重试。请求已发出后的超时、连接中断、非法或不完整响应统一保留“结果不确定”语义。
- 公共字段：`timeStamp`、`method`、`charset=utf-8`、`sign`、`check`、`bizContent`、`reqId`、`certId`、`version`。
- `reqId` 使用密码学随机前缀加当前时间尾缀生成；同一 Client 可并发安全使用。

## 5. 接口规格

| 能力 | method | version | 成功码 | 业务要求 |
| --- | --- | --- | --- | --- |
| 预下单 | `order.createOrder` | `1.4` | `subCode=0` | `mercId/busiCode/orderId/shopDate/amount/backUrl/payMode` 必填；支付宝生活号通道 26、微信小程序通道 29 |
| 交易查询 | `unify.online.trade.order.query` | `1.1` | `subCode=0000` | `orderId/tradeSn` 至少一个；均有值时订单号优先 |
| 退款 | `unify.trade.refund` | `1.0` | `subCode=0000` | 原订单号/流水至少一个，退款单号、日期、正分金额必填；同步成功只代表受理 |
| 退款查询 | `unify.trade.refund.query` | `1.1` | `subCode=0000` | 退款单号必填；仅普通退款，不开放分账退款 |

所有接口先要求网关公共响应 `code=00000`，再判断表内业务 `subCode`；任一层不成功均返回银盛明确拒绝错误。

金额公共输入和查询输出均为 `int64` 分。通知中以元为单位的十进制字符串严格转换为分：拒绝负数、科学计数法、两位以上小数和溢出，不使用浮点数。

正式环境已验证预下单解密结果可能是 `{ "rpcError": false, "data": { ... }, "suffixCode": 0 }`；预下单字段从 `data` 读取，微信场景同时保留完整、已验签并解密的根对象作为 `BusinessData`。为兼容官方参数表和实际响应，也接受字段直接位于根对象的历史形式。

支付宝结果返回银盛实际提供的拉起材料：`PayURL` 和 `EncryptedData` 至少一个非空；正式环境已观察到仅返回 `encryData` 的成功响应。微信结果必须包含可传给收银台小程序的完整 `BusinessData`，并校验嵌套业务字段中的 `encryData`；`appId` 按官方响应原样返回但不作为成功必要条件，因为前端接入文档允许业务侧配置收银台小程序原始 ID。公共模块不拼装 Flutter 路径，也不记录拉起材料。

## 6. 状态语义

- 交易成功：`00`。
- 交易处理中/未终结：`11/13/14/80/81`。
- 交易失败或已关闭：`50/93/95/97/98/99`。
- 未识别交易状态：`Unknown`，保留原始值，不猜测成功或失败。
- 退款成功：`00`。
- 退款处理中：`10`。
- 退款失败/关闭：`96/97/98/99`。
- 未识别退款状态：`Unknown`，保留原始值。

退款同步返回类型使用“受理”命名，不提供“退款成功”布尔值。最终状态必须由通知或退款查询确定。

## 7. 错误模型与安全不变量

公开哨兵错误支持 `errors.Is`：配置错误、请求校验错误、密码协议错误、签名错误、传输错误、响应结构错误、银盛明确拒绝、结果不确定。结构化网关错误只暴露 operation、code、subCode，不保留或输出上游报文、证书、密码、签名、`check` 和密文。

`ParsePaymentNotification` 是确定、无状态的解析函数；同一输入重复解析产生相同结果。公共模块不落库、不更新业务状态、不返回 HTTP `success`，这些职责属于业务仓。
