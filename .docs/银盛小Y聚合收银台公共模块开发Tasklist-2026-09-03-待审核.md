## 2. 不可变业务规则

以下规则贯穿规格、代码和测试：

1. `certId` 表示接口发起方，即二级代理商或供应商书面确认的服务商商户号。
2. `mercId` 表示本公司已完成签约的银盛二级商户，是银盛接口中的收款身份；底层微信/支付宝渠道商户号属于银盛。
3. `.pfx` 与 PFX 密码属于发起方签名凭据；银盛 `.cer` 用于密钥加密和银盛响应/通知验签。
4. 请求所需的真实证书、密码、发起方/银盛二级商户号和回调地址只存在于业务侧服务器的 Secret/密钥系统；实际微信/支付宝交易商户号属于银盛，不进入公共模块或业务仓配置。
5. 公共模块不读取固定文件路径、环境变量、配置中心或业务仓配置文件，只接收显式传入的证书字节和配置。
6. `busiCode` 使用银盛二级商户获批值：`00510102` 是聚合收银台 D0，`00510103` 是普通聚合收银台，不允许公共模块默认选择。
7. 支付宝生活号通道使用 `payMode=26`；微信 APP 拉起收银台小程序使用 `payMode=29`。两者均属于聚合收银台 APP 流程，不等同于支付宝原生 APP SDK 接口。
8. 金额在公共 Go API 中统一使用 `int64` 分；通知中的元金额使用十进制定点方式精确转换。
9. 客户端回跳不作为支付成功依据；服务端以验签通知和主动查询为准。
10. 网络超时、未知状态和解析异常保持“不确定”语义，不伪装成支付失败或成功。

## 3. SDD、BDD、TDD 开发要求

本 Tasklist 中，SDD 指 **Specification-Driven Development（规格驱动开发）**。

```text
SDD：先冻结协议和不变量
             │
             ▼
BDD：把业务行为写成 Given/When/Then
             │
             ▼
TDD：失败测试 → 最小实现 → 重构
             │
             ▼
规格、行为、测试同时验收
```

### 3.1 SDD 要求

每项能力在写生产代码前，必须先形成可审核规格：

- 输入、输出和必填字段。
- 字段到银盛报文的精确映射。
- 前置条件、后置条件和不变量。
- 成功、明确失败和结果不确定的判定。
- 敏感字段及其日志脱敏规则。
- 官方文档版本、样例或供应商书面确认来源。
- 至少一个正常示例和一个失败示例，全部使用占位值或官方测试向量。

规格有冲突时停止对应实现，先更新规格并重新审核，不允许让代码自行选择一种解释。

### 3.2 BDD 要求

BDD 场景使用 Given/When/Then 描述用户可观察行为，但不引入额外 BDD 框架。场景直接转成 Go 表驱动测试，保持依赖最少。

每个公开方法至少覆盖：

- 正常成功行为。
- 必填输入缺失或非法行为。
- 银盛明确拒绝行为。
- 网络或结果不确定行为。
- 篡改、伪造或敏感信息泄露行为。

BDD 场景编号必须出现在对应测试名称或注释中，便于从需求追溯到测试。

### 3.3 TDD 要求

每个开发任务遵循严格的 Red-Green-Refactor：

1. **Red**：先提交或展示失败测试，证明待实现行为尚不存在。
2. **Green**：只写让当前测试通过的最小生产代码。
3. **Refactor**：在测试保持通过的前提下消除重复、改善命名和错误边界。
4. 每个缺陷先补充可复现的失败回归测试，再修复生产代码。
5. 不通过跳过测试、弱化断言或改写期望结果让失败“消失”。
6. 测试不得访问真实银盛网关，不得使用生产证书或真实商户资料。

不设置只为追求数字的覆盖率门槛。验收以第 8 节行为矩阵全部覆盖、公开方法和安全错误分支无缺口为准，同时生成覆盖率报告供审核。

### 3.4 最小设计要求

- 只实现 `payment/ysepay`，不创建只有一个实现的 Payment Provider Registry。
- 优先使用 Go 标准库和仓库已有依赖。
- 除 PFX/国密协议确有需要外，不新增第三方依赖；新增依赖前记录必要性和替代方案。
- 使用自定义 `http.RoundTripper`、`httptest` 和表驱动测试，不引入 Mock 框架。
- 默认由业务仓读取证书文件并传入字节。没有真实 KMS/硬件签名需求时，不预先抽象通用签名平台。
- 不提供可绕过校验的 `map[string]any` 通用请求接口。

## 4. 计划中的最小公共 API

最终签名以 SDD 评审结果为准，当前预期最小能力如下：

```go
client, err := ysepay.NewClient(config)

order, err := client.CreateCashierOrder(ctx, request)
trade, err := client.QueryTrade(ctx, query)
refund, err := client.Refund(ctx, refundRequest)
refundState, err := client.QueryRefund(ctx, refundQuery)
notice, err := client.ParsePaymentNotification(payload)
```

配置和请求必须使用不含糊的命名：

- `InitiatorMerchantID` → `certId`。
- `PayeeMerchantID` → `mercId`。
- `BusinessCode` → `busiCode`。
- `SigningPKCS12` → 业务仓从 `.pfx` 读取的字节。
- `SigningCertificatePassword` → 业务仓从 Secret 读取的密码。
- `YsePublicCertificate` → 业务仓从 `.cer` 读取的字节。

公共 API 不接受证书路径，不内置截图中的任何真实编号或密码。

## 9. 核心 BDD 场景

### BDD-PAY-001：服务商发起、银盛二级商户收款

```gherkin
Given 业务仓使用 Secret 中的发起方证书和 InitiatorMerchantID 创建客户端
And 本笔订单指定已进件的 PayeeMerchantID 和获批 BusinessCode
When 公共模块创建银盛预下单请求
Then 公共字段 certId 等于 InitiatorMerchantID
And bizContent.mercId 等于 PayeeMerchantID
And 两个商户号不会互换
```

### BDD-PAY-002：支付宝 APP 支付

```gherkin
Given 一笔合法订单选择支付宝
When 银盛返回签名正确且包含 payUrl 或 encryData 的成功响应
Then 公共模块先验签再解密
And 兼容 data 嵌套结构并返回 payMode 26 和实际拉起材料
And 不返回证书、密码或完整银盛原始报文
```

### BDD-PAY-003：微信 APP 支付

```gherkin
Given 一笔合法订单选择微信
When 银盛返回签名正确的收银台小程序数据
Then 公共模块返回 payMode 29 和完整 businessData
And appId 存在时原样返回但不作为成功必要条件
And Flutter 所需数据不包含任何服务端签名凭据
```

### BDD-SEC-001：伪造支付通知

```gherkin
Given 通知中的任一已签名字段被修改
When 业务仓调用 ParsePaymentNotification
Then 公共模块返回验签错误
And 不返回可用于订单入账的成功事件
```

### BDD-NOT-001：重复支付通知

```gherkin
Given 同一份合法通知被重复提交
When 公共模块分别解析两次
Then 两次返回相同的已验证事件
And 公共模块不维护订单状态或执行权益发放
And 业务仓通过数据库事务完成幂等处理
```

### BDD-ERR-001：支付结果不确定

```gherkin
Given 请求已发送但银盛响应超时
When 公共模块无法确定银盛是否完成处理
Then 返回结果不确定错误
And 不返回支付失败或支付成功
And 业务仓可以使用同一业务订单发起交易查询
```

### BDD-REF-001：退款已受理但尚未终态

```gherkin
Given 一笔合法退款请求
When 银盛同步返回退款受理
Then 公共模块返回受理状态
And 不把受理状态描述为退款成功
And 业务仓通过退款查询确认最终状态
```

### BDD-SEC-002：业务服务器证书注入

```gherkin
Given PFX、密码和银盛 CER 存放在业务服务器 Secret 中
When 业务仓读取文件内容并创建公共客户端
Then 公共模块只接收内存中的证书材料
And 公共模块不读取固定路径或环境变量
And 错误和日志不包含凭据原文
```
